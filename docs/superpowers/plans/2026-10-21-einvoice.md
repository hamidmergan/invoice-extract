# E-invoice converter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn normal invoices (PDF, scan, photo) into valid XRechnung (CII XML) and ZUGFeRD (PDF with embedded CII) files, with AI extraction, a company profile, rule checks and a review UI.

**Architecture:** A new package `invoice_extract/einvoicing/` holds the typed model, the company profile, the field list and the row → model mapping, the rules, the CII builder (drafthorse) and the ZUGFeRD writer. Extraction reuses template mode (`extract_many(paths, EINVOICE_FIELDS)`). The CLI gets an `einvoice` command. The web app gets `/api/e/*` endpoints, and a converter page becomes `/`; the v2 field-selection page moves to `/table`.

**Tech Stack:** Python 3.9+, drafthorse (Apache 2.0; lxml, pypdf), existing invoice-extract core, FastAPI, plain JS.

**Spec:** `docs/superpowers/specs/2026-10-21-einvoice-design.md` (builds on the v1 and v2 specs).

## Global Constraints

- Python >=3.9: `Optional`/`List`/`Dict`, no `X | Y`, no `match`.
- Any OpenAI-compatible model; no provider-specific code; no default model.
- English for code, messages, UI, docs, tests, commits.
- Amounts are `Decimal`, never float; dates are `datetime.date`.
- Nothing invalid is written: `build_cii` and the writers refuse an invoice with error issues for the chosen format.
- No real invoices in the repo; fixtures come from `tests/pdfgen.py` or are built in the tests. The internal lab server URL never appears in the repo.
- Test command: `.venv/bin/pytest -q`.

## Review Focus

1. **Rounding:** lines whose quantity × price has more than 2 decimals, and several VAT rates on one invoice. The totals in the XML must satisfy BR-CO-10/13/15 exactly. Test in Task 1.
2. **Missing data for XRechnung** (buyer e-mail, buyer reference, seller contact): these must be errors that block the XRechnung download, while ZUGFeRD (EN 16931) may still be written. Test in Task 4.
3. **Direct debit invoices** (mandate reference, creditor ID, debited account) must map to payment means 59, with the BR-DE-24 fields. Tests in Tasks 3 and 5.
4. **Scans and photos as ZUGFeRD input:** the image becomes a PDF, then the XML is embedded. Test in Task 6.
5. **Hostile or odd model output in the lines** (text in amounts, missing quantity, a rate written as "19 %"): parsed or flagged, never a crash. Test in Task 3.

### Task 1: Model, tax groups, totals

**Files:** Create `src/invoice_extract/einvoicing/__init__.py`, `model.py`. Test `tests/test_einvoicing_model.py`.

**Interfaces (Produces):**
- `Party(name="", street="", postcode="", city="", country="", vat_id="", tax_number="", contact_name="", phone="", email="")`
- `Line(description="", quantity=Decimal("1"), unit="C62", unit_price=None, vat_rate=None, vat_category="", amount=None)`. `vat_category` "" means: derive S/E from the rate.
- `EInvoice(number="", type_code="380", issue_date=None, currency="EUR", seller=Party(), buyer=Party(), buyer_reference="", period_start=None, period_end=None, delivery_date=None, due_date=None, payment_terms="", payment_means="transfer"|"debit", iban="", bic="", mandate_reference="", creditor_id="", debited_iban="", exemption_reason="", notes=[], lines=[], printed_net=None, printed_vat=None, printed_gross=None)`
- `line_amount(line) -> Decimal`: `amount` if set, else round(quantity × unit_price, 2) (ROUND_HALF_UP).
- `category(line) -> str`: the explicit category, or "S" if the rate is above 0, else "E".
- `TaxGroup(category, rate, basis, tax)`; `tax_groups(inv) -> List[TaxGroup]`, ordered by (category, rate); tax = round(basis × rate / 100, 2).
- `Totals(line_total, tax_basis, tax_total, grand_total, due)`; `totals(inv) -> Totals`.
- `to_dict(inv) -> dict` (JSON-safe: Decimal and date as strings) and `from_dict(data) -> EInvoice` (accepts the strings back; bad numbers or dates raise `ConfigError` naming the field).

- [ ] Tests:
  - `test_totals_with_two_rates`: lines 3 × 3.333 at 19 % and 1 × 10.00 at 7 %. The line amounts are 10.00 and 10.00, the groups are S/7 (basis 10.00, tax 0.70) and S/19 (basis 10.00, tax 1.90), and the totals are 20.00 / 2.60 / 22.60.
  - `test_zero_rate_is_exempt`: rate 0 gives category E.
  - `test_dict_roundtrip`: `from_dict(to_dict(inv)) == inv`, and `from_dict` with `{"issue_date": "31.02.2025"}` raises `ConfigError` mentioning "issue_date".
- [ ] RED, implement, GREEN, full suite, commit `feat: add the e-invoice model`.

### Task 3: Fields and row mapping

**Files:** Create `einvoicing/fields.py`. Test `tests/test_einvoicing_fields.py`.

**Interfaces:**
- `LINE_FIELDS = ["Description", "Quantity", "Unit", "Unit Price", "VAT Rate", "Amount"]`
- `EINVOICE_FIELDS: List[Column]`: value columns with keys and hints for every `EInvoice` field. Seller and buyer parts are `seller_name`, `seller_street`, ..., `buyer_email`. Roles are set where they exist (`supplier`, `invoice_no`, `invoice_date`, `due_date`, `net`, `vat`, `gross`, `currency`, `iban`), so boxes and checks keep working. There is one table column `lines` with `table_columns=LINE_FIELDS`. Hints tell the model, among other things: the type is "credit note" or "invoice"; payment means is "direct debit" or "transfer"; the country is a 2-letter code.
- `UNIT_CODES`: maps lower-cased unit words (de/en: stk, stück, piece, pcs, h, std, stunde, hour, tag, day, monat, month, kg, l, liter, m, meter, pauschal) to UN/ECE codes. Unknown words give C62.
- `from_row(row: Row) -> EInvoice`:
  - takes the values from the cells;
  - parses amounts with `normalize("amount", ...)` and rates such as "19 %", "19,0" or "0.19" (a value ≤ 1 is a fraction, ×100);
  - a quantity defaults to 1, and a line without a description is skipped;
  - no lines but a printed net gives one line "Invoice <number>" with quantity 1, unit price = net, and rate = round(vat / net × 100) when both are known;
  - payment means is "debit" when the hint answer, a mandate reference or a creditor ID says so; the type code is 381 for credit notes;
  - a country name maps to an ISO code ("Deutschland"/"Germany" → DE; unknown text is left as it is, which is a rule error later).

- [ ] Tests:
  - `test_from_row_maps_parties_lines_and_payment`: a hand-built `Row` with cells for every part, lines with "2", "Std", "50,00", "19 %", "100,00", a mandate reference and a creditor ID. Expect quantity 2, unit HUR, unit price 50.00, rate 19, amount 100.00, payment means debit and country DE.
  - `test_from_row_without_lines_builds_one_line` (net 100.00, vat 19.00 → one line, rate 19).
  - `test_from_row_odd_line_values` (Review Focus 5): amount "abc" → `None`, quantity missing → 1, rate "" → `None`; no exception.
- [ ] RED, implement, GREEN, commit `feat: map extracted fields to the e-invoice model`.

### Task 4: Rules

**Files:** Create `einvoicing/rules.py`. Test `tests/test_einvoicing_rules.py`.

**Interfaces:**
- `Issue(field: str, level: str, rule: str, message: str)`. `field` is a dotted path such as `buyer.email`, `lines.2.vat_rate` or `iban`.
- `FORMATS = ("xrechnung", "zugferd")`
- `check(inv, format) -> List[Issue]`.
- **EN 16931 errors (both formats):**
  - mandatory: number, issue_date, currency (3 letters), seller name and country, buyer name and country, at least one line;
  - each line has a description, a quantity, a unit price, and a rate unless the category is E/Z;
  - seller VAT ID or tax number when a group has category S (BR-S-02);
  - an exemption reason for category E (BR-E-10);
  - due date or payment terms when the amount due is above 0 (BR-CO-25);
  - printed net/vat/gross must equal the computed totals within 0.01; a mismatch is an error on the field (`net`, `vat`, `gross`);
  - a line whose printed amount differs from quantity × price by more than 0.01 is an error on `lines.N.amount`.
- **XRechnung only:**
  - buyer_reference (BR-DE-15);
  - seller city, postcode and street (BR-DE-3, -4);
  - seller contact name, phone and email (BR-DE-2, -5, -6, -7);
  - seller email as electronic address (BT-34);
  - buyer email (BT-49);
  - payment means: a transfer needs an IBAN (BR-DE-23), a debit needs a mandate reference, a creditor ID and a debited IBAN (BR-DE-24);
  - for ZUGFeRD these are warnings, not errors.
- IBANs are checked with the existing mod-97 check (`checks.iban_valid`).

- [ ] Tests: a complete valid invoice gives `[]` for both formats. Then one test per group:
  - missing buyer email: an XRechnung error and a ZUGFeRD warning (Review Focus 2);
  - totals mismatch;
  - rate 0 without an exemption reason;
  - a debit without a mandate reference;
  - a bad IBAN.
- [ ] RED, implement, GREEN, commit `feat: check e-invoices against EN 16931 and XRechnung rules`.

### Task 5: CII XML

**Files:** Create `einvoicing/cii.py`. Modify `pyproject.toml` (dependency `drafthorse>=2025.1`). Test `tests/test_einvoicing_cii.py`.

**Interfaces:**
- `GUIDELINES = {"xrechnung": "urn:cen.eu:en16931:2017#compliant#urn:xeinkauf.de:kosit:xrechnung_3.0", "zugferd": "urn:cen.eu:en16931:2017"}`
- `build_cii(inv, format) -> bytes`. It raises `ConfigError` listing the error issues when `check(inv, format)` has errors. Otherwise it builds the drafthorse `Document` with every field the model has. The electronic addresses are e-mails with scheme `EM`. Payment means is 58 with the payee IBAN, or 59 with the mandate reference, creditor ID and debited IBAN. The output is serialized with `schema="FACTUR-X_EN16931"` (XSD check).
- `TYPE_CODES`: 380/381.

- [ ] Tests:
  - `test_build_cii_roundtrip`: the valid invoice from Task 4 builds without error. `einvoice.parse_xml(xml)` gives the same invoice number, gross, IBAN and supplier, and the guideline ID is in the XML for both formats.
  - `test_build_cii_refuses_invalid`.
  - `test_build_cii_direct_debit` (Review Focus 3): the XML contains `<ram:TypeCode>59</ram:TypeCode>`, the mandate reference and the creditor ID.
- [ ] Dev check (no test): write the XRechnung XML of the sample to the scratchpad and run the KoSIT validator via Docker (eclipse-temurin:17-jre, `validator.jar -s config/scenarios.xml -r config`). Expected: "acceptable". Fix until it is; ledger the result.

### Task 7: Library and CLI

**Files:** Modify `einvoicing/__init__.py` and `cli.py`. Test `tests/test_einvoicing_convert.py` and `tests/test_cli.py`.

**Interfaces:**
- `Conversion(path, invoice: Optional[EInvoice], row: Row, error: Optional[str])`, with `issues(format) -> List[Issue]`.
- `convert_many(paths, *, profile=None, base_url=None, model=None, api_key=None, vision_model=None, client=None, **limits) -> List[Conversion]`:
  - runs `extract_many(paths, EINVOICE_FIELDS, ...)`, then `from_row` and `apply_profile`;
  - an XML or ZUGFeRD input gives `error="Already an e-invoice"`.
- `write(conversion, format, out_dir) -> Path`. It writes `<stem>.xml` (xrechnung) or `<stem>.pdf` (zugferd) and refuses invalid invoices with `ConfigError`.
- CLI: `invoice-extract einvoice FILES [--format xrechnung|zugferd] [--profile FILE] [-o DIR] [model flags]`.
  - Per file, stderr shows `name: written <path>` or `name: <n> problems` followed by the issues.
  - The exit code is 0 when all files were written, 1 otherwise, and 2 on a setup error.
  - `-o` defaults to the current directory.

- [ ] Tests (fake server returns a complete extraction):
  - `convert_many` gives a valid invoice;
  - `write` produces a parseable XML;
  - CLI exit 0 and the file exists; a profile replaces the seller name;
  - an incomplete extraction gives exit 1 and lists "buyer.email".
- [ ] Live check: qwen3 on `samples/digital.pdf` (and on the owner's invoice if it is still in the server's temporary folder), then KoSIT on the XRechnung output after filling the missing fields in a profile. Ledger the result.

### Task 8: Web API

**Files:** Modify `web/app.py`. Test `tests/test_web_einvoice.py`.

**Interfaces** (same guard, lock and upload rules as the existing app):
- Workspace part: `e_files: Dict[str, EEntry(id, name, path, state, conversion, invoice)]`, `profile: Profile`, `format: str`.
- `POST /api/e/files` (multipart `files`): extract in the background, state pending → running → done.
- `GET /api/e/state` returns `{"profile": {...}, "format", "files": [{id, name, state, error, invoice: to_dict, boxes: {field: box}, issues: {xrechnung: [...], zugferd: [...]}}]}`. The boxes come from the row cells, keyed by the field path used in issues.
- `PUT /api/e/files/{id}` with `{"invoice": {...}}` runs `from_dict`; a bad value gives 400 naming the field. It returns the entry.
- `PUT /api/e/profile` (JSON) and `GET /api/e/profile.yaml`; `POST /api/e/profile` (YAML file). Profile changes are applied to every invoice, and fields edited by hand stay.
- `GET /api/e/files/{id}/download?format=xrechnung|zugferd` returns the file, or 409 with the issue list when there are errors.
- `DELETE /api/e/files`.
- The page endpoints `/api/files/{id}/pages...` find e-entries too.

- [ ] Tests: upload → state done with an invoice; PUT an edit; download with errors gives 409 and lists buyer.email; after the fix it gives 200 and valid XML; ZUGFeRD download is a PDF; the profile endpoints round-trip; unknown id 404; the guard still applies.
- [ ] RED, implement, GREEN, commit `feat: web API for the e-invoice converter`.
